# 02 — Identifier grammar and numbering

## Why

"Identyfikator" is how the legal department refers to a contract in e-mail, in
court filings and in conversation. It is generated by the system, it encodes
company / businessline / year / sequence, and annexes extend their parent's number.
Legacy implements the grammar as a SQL view (`contractview`) that every list sorts by
and that the next-number logic reads. That view was never ported, so today's
`lib/contracts/identifier.ts` is a reimplementation from observed shapes — close, but
with one latent bug and no shared parser for sorting.

Getting this wrong produces duplicate or out-of-sequence numbers on live contracts,
which is the kind of error the legal department notices immediately.

## Legacy behaviour

### The grammar, as executable code

`cru.sql:447511` — `contractview` decomposes every identifier into three numbers:

```sql
CREATE ALGORITHM=UNDEFINED SQL SECURITY INVOKER VIEW `contractview` AS
select
  abs(substring_index(`c`.`identifier`, '/', if((`c`.`type_id` = 5), -(3), -(2)))) AS `n_year`,
  abs(substring_index(replace(`c`.`identifier`, 'P', ''), '/',
                      if((`c`.`type_id` = 5), -(2), -(1))))                        AS `n_number`,
  if((`c`.`type_id` = 5),
     abs(substring_index(replace(`c`.`identifier`, 'A', ''), '/', -(1))), 0)       AS `n_anex`,
  /* … all 45 contract columns … */
from `contract` `c`;
```

Read it as:

- `type_id = 5` is `Aneks` (`contract_type` id 5). Annexes have one extra `/`-segment,
  so every offset shifts by one.
- `n_year` — second-from-last segment normally, third-from-last for an annex.
- `n_number` — last segment normally, second-from-last for an annex, with the literal
  `P` stripped first. So `P0481` and `0481` both yield `481`.
- `n_anex` — last segment with `A` stripped, `0` for anything that is not an annex.
- `abs()` on a `substring_index` result coerces the text to a number and swallows
  anything non-numeric as `0`.

The branch is on **document type**, not on the shape of the string. A record typed
`Aneks` whose identifier has no `/A` suffix parses with shifted offsets and yields
garbage; legacy tolerates that because `abs()` never throws.

### Prefix segments come from dictionary short names

| Source | Column | Values |
|---|---|---|
| `contract_company.company_short` | `Company.shortName` | `AMDSP`, `AMDP`, `AMC`, `HK POM`, `ST`, `SSC`, `(brak danych)`, and two inactive |
| `buissnesline.name_short` | `Businessline.shortName` | `DYS` (for `DYSTRYBUCJA`), `SSC`, null for `---` |

`Businessline.name` is `DYSTRYBUCJA`; `Businessline.shortName` is `DYS`. Confirmed in
`prisma/schema.prisma` — the field exists and carries the comment
`// "DYS", "SSC" — the segment used in identifiers`.

### Identifiers are not unique

111 identifiers appear more than once across the 20,626 rows (verified: see
Verification query 1). `Contract.identifier` is deliberately not `@unique`. Legacy
never enforced uniqueness either, and the duplicates are historical — the numbering
logic must not assume it can look a record up by identifier.

## Legacy quirks

### Quirk: prefix builder uses the long name instead of the short one

- **Current code:** `lib/contracts/identifier.ts:110` —
  `const parts = [company?.shortName, businessline?.name]`.
- **Why it is wrong:** `Businessline.name` is `DYSTRYBUCJA`, not `DYS`. The first
  record ever created for a company+businessline pair would be numbered
  `AMDSP/DYSTRYBUCJA/2026/0001` instead of `AMDSP/DYS/2026/0001`.
- **Why it has not fired:** the branch only runs when `prefixFromYear === -1`, i.e.
  when the series has no prior record at all. Every live series already has one, so
  the code path is dormant. It would fire on the first contract for a new
  businessline, or in a fresh database.
- **We do:** use `businessline?.shortName ?? businessline?.name` — falling back to the
  long name only if `shortName` is null, which is the case for `---` (id 1).
- **Sign-off:** not needed, a bug fix with no visible change to existing data.

### Quirk: `abs()` silently turns unparseable segments into zero

- **Legacy:** `contractview` wraps every extraction in `abs()`, so `2019/U/0466`
  yields `n_year = 0` rather than failing.
- **Why it matters:** 453 records use non-numeric middle segments (`9999/U/9999`,
  `9999/P/9999`, `9999/C/9999`, `9999/S9999`). Under legacy's parser they all sort as
  year 0 and cluster at the top or bottom of any sorted list.
- **We do:** parse to `null` rather than `0`, and sort nulls last. This is a visible
  behaviour change on those 453 records, but only in sort position.
- **Sign-off:** not needed; document it in the spec-09 sort notes.

### Quirk: the annex branch keys on document type, not on the string

- **Legacy:** the `if (type_id = 5)` branch assumes every `Aneks` has an `/A99`
  suffix and every non-annex has none.
- **Why it matters:** the assumption does not hold. There are records typed `Aneks`
  without the suffix, and the offsets then read the wrong segments.
- **We do:** parse the string shape, and use `documentType` only to *validate* —
  flagging a mismatch rather than mis-parsing.
- **Sign-off:** not needed.

### The parser

One exported function replacing the two private regexes, returning the same three
numbers `contractview` produces plus the prefix:

```ts
export interface ParsedIdentifier {
  /** Everything before the year segment, e.g. "AMDSP/DYS" or "HK POM". Null when absent. */
  prefix: string | null;
  /** Null when the segment is not numeric — legacy's abs() would return 0 here. */
  year: number | null;
  /** The P prefix on the sequence marks a project. */
  isProject: boolean;
  sequence: number | null;
  /** 0 when the identifier carries no /A suffix, matching legacy's n_anex. */
  annex: number;
}

export function parseIdentifier(identifier: string): ParsedIdentifier;
```

It must handle every shape in the table above, including the leading-empty-segment
forms (`/2019/P0134`, 23 records) and the space inside `HK POM`.

The same function backs sorting (spec 06 "sort by identifier" and spec 09) so the
list order matches what the numbering logic believes.

### Replacing the 2000-row scan

`nextRecordIdentifier` currently pulls up to `SERIES_SCAN_LIMIT = 2000` rows of a
series and scans them in memory (`identifier.ts:67-93`). The comment is right that
text sorting confuses 999 with 1000 — but the fix is a computed comparison in SQL,
not a bounded scan. The biggest series (`AMDSP/DYS` projects) already exceeds 2,800
rows, so the cap can silently miss the real maximum.

Replace with a single query that extracts the sequence for the target series and year
and takes the max, using the same decomposition the parser implements. A raw query is
acceptable here; the alternative is a generated column, which `contractview` is the
legacy equivalent of.

Keep the existing prefix rule — the newest prefix in the series wins, so a change of
convention does not travel backwards in time (`identifier.ts:87-91`). That rule is
correct and is why `composePrefixFromDictionaries` is only a fallback.

### Annex numbering

`nextAnnexIdentifier` (`identifier.ts:119`) already numbers by scanning siblings
rather than counting them, so a deleted annex does not have its number reused. That
is correct and verified — record 21235 is a soft-deleted `A01` and the next annex on
umowa 21228 became `A02`. Keep it. Two changes only:

- pad to 2 digits as now (`A01`), but accept 1–3 digits when parsing, since
  `ANNEX_PAD` is a formatting choice and legacy data may carry `A001`;
- exclude soft-deleted siblings from the *maximum* only if Mati wants numbers reused
  (he does not — see the verified behaviour above). Document the decision in place.

## Verification

```sql
-- 1. Duplicate identifiers: a known, accepted condition.
select count(*) from (
  select identifier from "Contract" where identifier is not null
  group by identifier having count(*) > 1
) d;
-- expected: 111

-- 2. Shape census — regenerate after any parser change and diff against this spec.
select regexp_replace(regexp_replace(identifier, '[0-9]', '9', 'g'),
                      '[A-Z]{2,6}', 'C', 'g') as shape, count(*)
from "Contract" where identifier is not null
group by 1 order by 2 desc;
-- expected: the 18 rows in the table above, same counts

-- 3. Every annex identifier extends its parent's.
select count(*) from "Contract" a join "Contract" p on p.id = a."parentId"
where a.identifier is not null and p.identifier is not null
  and a.identifier not like p.identifier || '/A%';
-- capture the current number before changing anything; it must not grow

-- 4. Businessline short names are present where identifiers need them.
select id, name, "shortName" from "Businessline" order by id;
-- expected: 1 '---' null, 2 'SSC' 'SSC', 3 'DYSTRYBUCJA' 'DYS'
```

## Open questions

1. **Padding width for new numbers.** `SEQUENCE_PAD = 4` matches the dominant shape
   (`0006`, `P0481`). Confirm nothing in the series has passed 9999 — if a company
   ever reaches five digits the format silently widens.
2. **Is the identifier editable on the form?** It currently is, in every mode, which
   Mati asked for. That is why hand-entered shapes like `2026/U/0013` keep appearing
   (13 records in 2026). Confirm this stays, because it is the reason uniqueness can
   never be enforced.
3. **Year source.** `nextRecordIdentifier` defaults to `new Date().getFullYear()`.
   Legacy appears to do the same, but a contract registered in January for the
   previous year's series would need an override. Nobody has asked for one.
